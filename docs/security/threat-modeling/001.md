# ADR 001: Modelado de amenazas para la migración del módulo "Obtener producto por identificador" 

- **Estado:** Propuesto
- **Fecha:** 2026-11-17
- **Autor:** Andrea Bañuelos Ochoa


## Contexto (¿En qué estamos trabajando?)
El equipo de desarrollo quiere realizar la migración de diversos módulos de Productos a diversos microservicios; en específico, el enfoque esta en el primer módulo que es **obtener producto por identificador**, 
para lo cual se debe realizar el modelado de amenazas **STRIDE** para identificar de forma preventiva posibles amenazas y buscar mitigarlas como parte del diseño.


## Revisión de Riesgos (¿Qué puede salir mal?)
El módulo de **obtener producto por identificador** es un método GET que tiene acceso público, cuenta con datos de entrada y salida, como se muestra a continuación:
- Método: **get**
- Endpoint: **/api/v1/products/{id}**
- Acceso: **público**
- Descripción: **Obtiene el detalle de un producto.**
- Datos Entrada: **Path: id (UUID o Integer) / Body: Ninguno**
- Datos Salida: **Sin especificar**

Para poder identificar las posibles amenazas se debe crear un **Diagrama de Flujo de Datos** (DFD) donde se ve la interacción de los componentes y el flujo que seguirá el proceso a analizar. Se identifican 6 componentes/capas a analizar, estas son:
- Cliente
- Capa de Internet
- Gateway API
- Capa de red interna
- Microservicio (getProductsById)
- Base de datos

El DFD se puede ver de la siguiente forma:

          Internet               R.Interna                      _______________
             |                      |                           |             |
[Cliente] -- | --> [Gateway API] -- | --> [Microservicio] ----> |Base de Datos|
             |                      |                           |_____________|

Identificando cada componente, debemos aplicar **STRIDE** en cada uno. Para lo cual tendriamos el siquiente analisis:

1. Cliente
    - Amenaza STRIDE:
        a) Spoofing
        b) Repudiation
    - Escenario:
        a) Usar credenciales robadas.
        b) Negar que hizo alguna operación con su usuario.
    - Mitigación:
        a) **Autenticación doble factor** en el frontend.
        b) Tener una **bitácora de acceso** (Usuario e IP), y manejar tiempo de **expiración de las sesiones**.
2. Capa de Internet
    - Amenaza STRIDE: Tampering
    - Escenario: Que puedan hackear la petición en el tránsito por internet.
    - Mitigación: Utilizar protocolos seguros como **HTTPS**. Puesto que es un servicio que en su cuerpo lleva el ID, **encriptar** los datos de entrada antes de enviar la solicitud.
3. Gateway API
    - Amenaza STRIDE:
        a) Denial of Service
        b) Information Disclosure
    - Escenario:
        a) Diversos atacantes saturen la API con peticiones.
        b) La API se encuentre abierta a obtener datos adicionales por medio del parámetro de entrada en el endpoint por ser GET.
    - Mitigación:
        a) Agregar **token** con tiempo de expiración. Establecer **límite de peticiones por minuto** para evitar el bloqueo. 
        b) Puesto que es un servicio que en su cuerpo lleva el ID, **encriptar** los datos de entrada antes de enviar la solicitud.
4. Capa de Red Interna
    - Amenaza STRIDE:
        a) Tampering
        b) Information Disclosure
    - Escenario:
        a) Que tengan acceso a la red interna.
        b) La API se encuentre abierta a obtener datos adicionales por medio del parámetro de entrada en el endpoint por ser GET.
    - Mitigación:
        a) y b) Puesto que es un servicio que en su cuerpo lleva el ID, **encriptar** los datos de entrada antes de enviar la solicitud.
5. Microservicio
    - Amenaza STRIDE: Spoofing
    - Escenario: Acceso público directo al microservicio sin pasar por el Gateway API.
    - Mitigación: Quitar el acceso público. Validar que **siempre** venga del **origen Gateway API**.
6. Base de Datos
    - Amenaza STRIDE:
        a) Tampering
        b) Information Disclosure
    - Escenario:
        a) Modificación de registros sin autorización.
        b) Acceso no autorizado a información adicional a la que se solicita.
    - Mitigación:
        a) **Validar los datos de entrada con ESAPI** para que correspondan al tipo y nomenclatura esperada (los datos no deben ser queries).
        b) **Usuarios** de BD con **privilegios mínimos** requeridos a objetos de la BD.

      
## Consecuencias (¿Qué vamos hacer al respecto?)
### Positivas
- Validaciones del origen de la autenticación para asegurar que sea el usuario autorizado.
- Control de sesiones utilizadas y sin utilizar para la optimización de recursos y acceso.
- Protección de los datos que se envían para consultar.
- Aseguramiento de la integridad de los datos durante todo el flujo.
  
### Negativas
- Mayor costo en la implementación de la seguridad
- Aumento en el mantenimiento de la operación.


### Desafíos/Retroalimentación del análisis (¿Hicimos un buen trabajo?)
- Se desconocen algunos datos del contexto del flujo para poder hacer un análisis mas profundo.
- Obtener presupuesto para dichas mitigaciones en la solución.
